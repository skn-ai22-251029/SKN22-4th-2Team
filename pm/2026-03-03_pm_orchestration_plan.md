# PM Orchestration Plan: 빌드 및 운영 환경 통신 정상화

이 문서는 상용 환경의 '네트워크 연결 오류'를 해결하기 위한 단계별 실행 계획입니다. 모든 에이전트는 아래 순서와 지침을 엄격히 준수해 주십시오.

## 🚀 단계별 실행 로드맵

### 1단계: 프론트엔드 빌드 블로커 해제 (P0 - Frontend Agent)

빌드가 성공해야 배포가 가능하므로 가장 먼저 처리합니다.

- **Task**: `useRagStream.ts`에서 사용하는 `SERVER_ERROR` 타입을 `ErrorFallback.tsx`의 `ErrorType` 유니온에 추가.
- **주의**: 단순 타입 추가에 그치지 말고, `npm run build`를 로컬에서 실행하여 `exit code 0`을 확인하십시오.
- **메시지**: _"프론트엔드 빌드 시 발생하는 TypeScript 타입 오류를 해결해 주세요. `SERVER_ERROR` 타입을 유니온에 포함하고 빌드 성공 여부를 리포트해 주세요."_

### 2단계: 운영 환경 연결 및 CORS 안정화 (P0 - DevOps Agent)

빌드된 이미지가 배포된 후 통신이 되도록 설정합니다.

- **Task**: `infra/ecs/task-definition-template.json`의 `ALLOWED_ORIGINS` 값을 `*`로 업데이트 (초기 도메인 유동성 대응).
- **Hardcoding 금지**: 특정 ALB 주소를 코드에 넣지 마세요. 주입된 환경변수를 백엔드가 유연하게 처리하도록 구성되어 있는지 확인하십시오.
- **메시지**: _"운영 환경의 새로운 ALB 주소에 대응할 수 있도록 ECS Task Definition의 환경변수를 업데이트해 주세요. 주소 하드코딩 대신 와일드카드 또는 동적 주입 방식을 사용하세요."_

### 단계 3: 에러 상세 정보 가시성 확보 (P1 - Frontend & Backend)

장애 발생 시 빠른 원인 파악을 위해 UX를 개선합니다.

- **Task**: 백엔드 500 에러 시 JSON 응답에 `detail` 필드를 포함하고, 프론트엔드는 이를 파싱하여 화면에 표시.
- **메시지**: _"네트워크 오류 발생 시 사용자에게 구체적인 실패 사유를 노출할 수 있도록 백엔드 응답 포맷과 프론트엔드 파싱 로직을 동기화해 주세요."_

## 🛠️ 공통 원칙

- **Zero Hardcoding**: API 주소는 절대 하드코딩하지 않습니다. 프론트엔드는 `import.meta.env.VITE_API_BASE_URL`이 없으면 상대 경로(`/api/v1/...`)를 사용하도록 구현하십시오.
- **Verification**: 각 단계 완료 후 반드시 빌드 및 통신 테스트 결과를 공유하십시오.
